# 任务间队列通信说明

适用版本：V1.8.0.260920。更新日期：2026-09-20。

## 1. 文档目的

本文档说明工程中八个 FreeRTOS 任务间队列的生产者、消费者、消息类型、使用方式和异常处理。

本工程有三个主要业务任务：

- `HostCanStack`：负责上位机 CAN 通信、CAN_USER 协议解析、查询回复和写请求生命周期。
- `ControlTask`：负责请求有效性检查、CAN 业务命令与 MFC 执行命令之间的转换、结果码映射。
- `MfcTask`：负责RS485/EX201与MCP2515/CAN_USER自动识别、六路轮询、设定流量写入及读回。两个下行后端都属于此任务，不占用上位机CAN任务。

八个队列均使用 `xQueueCreateStatic()` 创建，队列容量均为 1，消息按值复制，不在队列中传递任务私有上下文的指针。

## 2. 队列总览

```text
                         host_command_queue
HostCanStack  ---------------------------------------->  ControlTask
     ^                                                        |
     |                  host_result_queue                     | command_queue
     +--------------------------------------------------------+
                                                              v
                                                           MfcTask
                                                              |
                         result_queue                         |
ControlTask   <-----------------------------------------------+


ControlTask   ----------- valve_state_queue ------------> HostCanStack

MfcTask       ----------- telemetry_queue ---------------> HostCanStack

HostCanStack  -------- control_state_queue --------------> ControlTask
HostCanStack  ---------- mfc_state_queue -----------------> MfcTask
```

| 队列 | 生产者 | 消费者 | 消息类型 | 写入方式 | 用途 |
| --- | --- | --- | --- | --- | --- |
| `host_command_queue` | HostCanStack | ControlTask | `A_HostCan_Command` | `xQueueSendToBack` | 传递已解析的 CAN 写请求 |
| `command_queue` | ControlTask | MfcTask | `A_MFC_Command` | `xQueueSendToBack` | 传递 MFC 可执行命令 |
| `result_queue` | MfcTask | ControlTask | `A_MFC_CommandResult` | `xQueueSendToBack` | 返回 MFC 实际执行结果 |
| `host_result_queue` | ControlTask | HostCanStack | `A_Control_Host_Result` | `xQueueSendToBack` | 返回已映射的 CAN_USER 业务结果 |
| `valve_state_queue` | ControlTask | HostCanStack | `A_HostCan_System` | `xQueueOverwrite` | 九阀输出、目标、吸合阶段及GPIO故障 |
| `telemetry_queue` | MfcTask | HostCanStack | `A_System_Telemetry` | `xQueueOverwrite` | 发布六路 MFC 最新完整快照 |
| `control_state_queue` | HostCanStack | ControlTask | `A_Control_Host_State` | `xQueueOverwrite` | 发布 CAN 请求的最新有效状态 |
| `mfc_state_queue` | HostCanStack | MfcTask | `A_Control_Host_State` | `xQueueOverwrite` | 供 MFC 执行前和执行中复核请求有效性 |

## 3. `host_command_queue`

### 3.1 通信方向

```text
HostCanStack -> ControlTask
```

### 3.2 消息内容

队列元素类型为 `A_HostCan_Command`：

```c
typedef struct
{
    uint32_t sequence;
    uint32_t started_ms;
    uint32_t index;
    uint32_t value;
    uint32_t valve_target;
    A_HostCan_Operation operation;
} A_HostCan_Command;
```

- `sequence`：MCU 内部请求号，用于匹配命令和结果，不增加到 CAN 线上协议中。
- `started_ms`：HostCanStack 接受请求的时间，后续转发不得重置总期限。
- `index`：MFC 通道或阀门索引。
- `value`：CAN_USER 报文中的 32 位原始数据。流量写入时为 `float32` 的位模式。
- `valve_target`：归一化后的九阀完整目标，当前没有阀门执行器接入。
- `operation`：请求操作类型。当前 ControlTask 仅接受 `A_HOSTCAN_COMMAND_SET_FLOW`。

### 3.3 生产和消费

HostCanStack 在 `A_System_ProcessHostCan()` 中调用 `A_HostCan_TakeCommand()` 提取已解析命令，然后使用 `xQueueSendToBack()` 发送。

ControlTask 在 `A_Control_Process()` 中使用 `xQueueReceive()` 领取。

如果队列已满，HostCanStack 不覆盖旧命令，而是以 `A_HOSTCAN_CODE_BUSY` 完成当前请求。

## 4. `command_queue`

### 4.1 通信方向

```text
ControlTask -> MfcTask
```

### 4.2 消息内容

队列元素类型为 `A_MFC_Command`：

```c
typedef struct
{
    uint32_t sequence;
    uint32_t index;
    A_MFC_CommandOperation operation;
    float target_flow;
    TickType_t started_tick;
    TickType_t timeout_ticks;
} A_MFC_Command;
```

- `sequence`：原 CAN 请求号。
- `index`：MFC 通道索引 `0～5`。
- `operation`：MFC 可执行操作，当前为设置目标流量。
- `target_flow`：按本通道单位表示的浮点工程值。
- `started_tick`：原 CAN 请求起点。
- `timeout_ticks`：包含排队、RS485 通信和读回确认的总期限。

### 4.3 转换过程

ControlTask 将 `A_HostCan_Command.value` 中的 32 位位模式还原为浮点工程值：

```c
g_command.target_flow = F_CanUser_BitsToFloat(g_host_command.value);
```

然后通过 `xQueueSendToBack()` 送入 `command_queue`。MfcTask 只在写状态为 `A_MFC_WRITE_IDLE` 时取出新命令。

如果队列已满，ControlTask 不覆盖旧命令，而是生成 `A_HOSTCAN_CODE_BUSY` 结果。

## 5. `result_queue`

### 5.1 通信方向

```text
MfcTask -> ControlTask
```

### 5.2 消息内容

队列元素类型为 `A_MFC_CommandResult`：

```c
typedef struct
{
    uint32_t sequence;
    A_MFC_CommandCode code;
    A_EX201_Result transport_result;
} A_MFC_CommandResult;
```

- `sequence`：关联原 CAN 请求，防止迟到结果完成后续新请求。
- `code`：MFC 业务执行结果，如成功、离线、超时、越界或读回不一致。
- `transport_result`：具体 EX201 事务结果，供调试和故障分类使用。

MfcTask 在命令到达 `A_MFC_WRITE_DONE` 后尝试发送结果。只有成功入队后才调用 `A_MFC_ReleaseCommand()` 释放命令槽。

如果队列已满，MfcTask 保留 `A_MFC_WRITE_DONE` 和完整结果，后续循环重试，不丢弃执行结果。

## 6. `host_result_queue`

### 6.1 通信方向

```text
ControlTask -> HostCanStack
```

### 6.2 消息内容

队列元素类型为 `A_Control_Host_Result`：

```c
typedef struct
{
    uint32_t sequence;
    uint32_t code;
} A_Control_Host_Result;
```

- `sequence`：原 CAN 请求号。
- `code`：已由 `A_Control_MapResult()` 映射成 CAN_USER 协议业务码的结果。

HostCanStack 收到后调用 `A_HostCan_CompleteCommand()`，校验请求号和总期限，再生成 CAN 写回复。

如果队列已满，ControlTask 将结果保留在 `pending_result`，设置 `result_pending`，本轮不领取新命令，后续循环继续发送。

## 7. `telemetry_queue`

### 7.1 通信方向

```text
MfcTask -> HostCanStack
```

### 7.2 消息内容

队列元素类型为 `A_System_Telemetry`：

```c
typedef struct
{
    A_HostCan_Channel channels[A_HOSTCAN_CHANNEL_COUNT];
    uint32_t link;
    uint32_t ready;
} A_System_Telemetry;
```

- `channels[6]`：六路 MFC 的最新完整快照，包括实际流量、设定读回、目标流量、量程、单位、小数位、在线状态、内部阀状态、报警和数据有效位。
- `link`：下行 MFC 链路状态。
- `ready`：MFC 执行入口是否就绪，不表示每台仪器都在线。

MfcTask 在任一通道快照、链路状态或就绪状态变化时，使用 `xQueueOverwrite()` 发布完整快照。

HostCanStack 出队后，更新自己的 `A_HostCan_Context.channels[]` 缓存。上位机的 CAN 读请求读取该缓存，不会临时发起 RS485 查询。

该队列只关心最新数据，因此允许新快照覆盖尚未消费的旧快照。每条消息都包含全部六路数据，不会因单路更新而丢失其他通道的当前值，但允许跳过中间版本。

## 8. `control_state_queue`

### 8.1 通信方向

```text
HostCanStack -> ControlTask
```

### 8.2 消息内容

队列元素类型为 `A_Control_Host_State`：

```c
typedef struct
{
    uint32_t sequence;
    TickType_t started_tick;
    TickType_t updated_tick;
    uint32_t valid;
} A_Control_Host_State;
```

- `sequence`：当前 CAN 写请求号。
- `started_tick`：原请求起点。
- `updated_tick`：HostCanStack 最近一次发布状态的时间。
- `valid`：请求号、CAN 硬件状态和总期限等检查通过时为非 0。

ControlTask 在转发新命令前调用 `A_Control_RequestValid()` 检查：

- `sequence` 是否一致。
- `started_tick` 是否一致。
- `valid` 是否为非 0。
- HostCanStack 状态是否超过 20 ms 没有更新。
- 请求总时间是否超过 3000 ms。

该队列用 `xQueueOverwrite()` 发布，因为只需要最新授权状态。

## 9. `mfc_state_queue`

### 9.1 通信方向

```text
HostCanStack -> MfcTask
```

### 9.2 消息内容

队列元素类型与 `control_state_queue` 相同，均为 `A_Control_Host_State`。

MfcTask 在实际执行写操作前和执行过程中复核原 CAN 请求是否仍然有效。如果 CAN 任务停止更新、CAN 故障、请求被撤销或总期限到期，MfcTask 不得使用旧授权继续启动新的物理写操作。

`control_state_queue` 和 `mfc_state_queue` 不能合并成一个队列，因为 `xQueueReceive()` 会移除消息。ControlTask 和 MfcTask 都必须独立获得同一份最新状态：

```text
                         +-> control_state_queue -> ControlTask
HostCanStack -> state ---+
                         +-> mfc_state_queue ----> MfcTask
```

## 10. 完整流量写入链路

以上位机设置第三路目标流量为例：

```text
1. HostCanStack 解析 CAN 写请求
       |
       | A_HostCan_Command
       v
   host_command_queue

2. ControlTask 检查请求有效性，将 32 位数据还原为 float
       |
       | A_MFC_Command
       v
   command_queue

3. MfcTask 执行 RFSM、WSFD、RSFD 及读回比对
       |
       | A_MFC_CommandResult
       v
   result_queue

4. ControlTask 将 MFC 结果映射为 CAN_USER 业务码
       |
       | A_Control_Host_Result
       v
   host_result_queue

5. HostCanStack 核对 sequence，生成 CAN 写回复并发送给上位机
```

执行期间，HostCanStack 同时通过两个独立覆盖队列发布请求有效状态：

```text
HostCanStack -> control_state_queue -> ControlTask
HostCanStack -> mfc_state_queue ----> MfcTask
```

MfcTask 完成写入并读回确认后，先通过 `telemetry_queue` 发布最新六路快照，再通过 `result_queue` 发送执行结果，使 HostCanStack 在处理成功结果时能取得已确认的最新数据。

## 11. 队列满时的处理

| 队列 | 队列满时的处理 |
| --- | --- |
| `host_command_queue` | 新 CAN 写请求返回 `BUSY` |
| `command_queue` | ControlTask 生成 `BUSY` 结果 |
| `result_queue` | MfcTask 保留 `DONE` 结果，后续重试，不释放命令槽 |
| `host_result_queue` | ControlTask 保留 `pending_result`，不领取新命令 |
| `telemetry_queue` | 新完整快照覆盖旧快照 |
| `control_state_queue` | 新状态覆盖旧状态 |
| `mfc_state_queue` | 新状态覆盖旧状态 |

## 12. 静态队列和按值复制

队列控制块和存储区都放在 `A_System_Context` 中：

```c
StaticQueue_t command_queue_memory;
uint8_t command_storage[sizeof(A_MFC_Command)];
QueueHandle_t command_queue;
```

这种设计的特点：

- 队列创建不依赖 FreeRTOS 动态内存。
- 存储容量在编译时确定。
- 不会因长期运行产生堆碎片。
- 队列内保存结构体副本，发送方的局部变量在函数返回后消失，不会影响已入队数据。
- 任务间不共享对方的业务上下文指针。

所有发送和接收操作的等待时间均为 `0U`，即非阻塞操作。队列空或队列满时立即返回，不阻塞当前任务。

## 13. 与模块内部环形缓冲区的区别

除八个 FreeRTOS 任务间队列外，CAN 模块还有两个内部缓冲区。它们不是 FreeRTOS 队列。

### 13.1 CAN 接收环形队列

```c
H_HostCan_Frame receive[H_HOSTCAN_RX_CAPACITY];
```

- 容量：16 帧。
- 生产者：`H_HostCan_Callback()` CAN 接收中断回调。
- 消费者：HostCanStack 通过 `H_HostCan_Receive()` 取帧。
- 同步方式：读取时使用 FSP 临界区保护索引和计数。

### 13.2 CAN 应用发送环形队列

```c
F_CanUser_Frame transmit[A_HOSTCAN_TX_CAPACITY];
```

- 容量：32 帧。
- 生产者：HostCanStack 的 `A_HostCan_QueueReply()`。
- 消费者：`A_HostCan_ServiceTransmit()`。
- 内容：已经过 `F_CanUser_Encode()` 编码的 CAN_USER 报文。
- 作用：一次连续读可以产生多帧回复，软件队列保存待发帧，并逐帧交给 CAN 硬件。

三类通信资源的边界为：

```text
CAN中断 -> H_HostCan.receive[16] -> HostCanStack

MfcTask / ControlTask / HostCanStack
             <-> 八个 FreeRTOS 队列 <->

HostCanStack -> A_HostCan.transmit[32] -> CAN硬件
```

FreeRTOS 队列用于任务之间隔离业务数据；两个内部环形缓冲区用于匹配 CAN 中断、业务处理和异步硬件发送的速度。

## 15. valve_state_queue与阀门命令

ControlTask通过A_Control_PublishValveState发布完整九阀快照，HostCanStack通过A_System_ReceiveValveState消费。长度1的覆盖队列用于最新状态，不保存每一次GPIO变化历史。CAN侧收到执行结果时会再次取最新状态，保持状态先于成功回复更新。

阀门命令沿用host_command_queue进入ControlTask，调用A_Valve模块执行；不经过Control到MFC的command_queue。执行结果沿用host_result_queue。A_Control_Queue_Set现在包含六个句柄，A_Control_Context.p_valve仅绑定同任务独占的状态，不允许CAN直接访问。

即使结果队列满，ControlTask也先推进阀门200ms计时，再重试结果发送。MFC六路遥测与阀状态使用不同覆盖队列，互不覆盖。

V1.8.0保持八个任务间队列。H_MfcCan的四帧接收缓冲和单个待发槽仅供MfcTask内部使用；SPI回调只置完成/错误标记。CAN0收到的上位机写命令仍经过host_command_queue、command_queue进入MFC，结果沿反向队列返回；下行CAN原始帧不跨任务透传。
